# 售前商品问答能力与评估边界

更新时间：2026-10-09。当前仅覆盖 ClickyCanvas 本地 6 款演示商品；此文档描述本阶段可验证的能力，不代表真实店铺表现。

## 顾客任务

| 顾客要做的事 | 期待行为 | 可核对的事实 |
| --- | --- | --- |
| 问店里有没有某种键盘或属性 | 直接查商品，不要求先提供预算；没有时明确说明 | 商品名称、轴体、配列、连接方式、兼容系统 |
| 给部分条件，请客服推荐 | 用已知条件展示候选和依据；预算可后补 | 硬条件不能被违反，偏好只影响排序 |
| 分步补充或修改条件 | 保留本页上下文，新条件覆盖同字段旧值 | 候选集与排序随条件变化 |
| 追问某款或比较两款 | 识别明确名称、ID、序号；指代不清则追问 | 回答只引用被问商品的目录字段 |
| 问目录没有的性能 | 说明资料不足，不能推测 | 本目录没有分贝、延迟、热插拔实测数据 |

“宿舍”是使用环境线索，不自动等同于“必须静音”；“青轴”是轴体查询，不应被当作预算澄清。独立数字键盘不混入普通整键盘推荐，但在明确询问数字键盘时参与筛选。

## 事实与理解的分工

商品目录是价格、规格、兼容性和候选范围的唯一事实来源。规则处理明确的常见字段；启用 DeepSeek 时，每条选购消息还可获得有原话证据的补充条件。代码验证字段、冲突和商品数据后才使用，规则中已确定的字段优先。模型失败时使用已确定的条件，不编造商品事实。订单验证码、政策依据与售后动作继续由原有流程处理。

## 评估办法

`data/shopping_cases.json` 是对话级案例集，保留 `source` 区分用户现场观察与人工设计。每轮检查意图、条件、期望商品 ID、顺序和关键回答；`scripts/evaluate_shopping.py` 将失败归为需求理解、候选召回、排序或回答。对话案例的候选 ID 由人工基于 `data/catalog.json` 标注；脚本还从目录原始字段衍生每款商品的价格、轴体、Mac 兼容性和各轴体库存探针，不调用被测筛选实现生成期望。用户实际问法作为回归案例保留，不改写成系统容易通过的句子。

验收同时运行多轮选购、原有业务评估、政策检索、单元测试，并在浏览器检查自然对话和窄屏。自动通过率只说明覆盖到的行为符合预期；独立顾客是否觉得有帮助需要另外抽样评价。下一轮应从真实或未参与开发的试用者收集问法，观察重复追问、无法回答和人工转交比例，再决定能力扩展。当前没有真实顾客数据，不能声称达到生产客服质量。
